# Android client

The app is a thin Kotlin shell around the same Rust engine the desktop daemon uses.

```
android/
  app/src/main/java/dev/intergalactic/app/
    EngineHolder.kt   # owns the Rust engine, persists state, forwards callbacks
    IgVpnService.kt   # VpnService: builds the TUN with every joined network's address and route
    MainActivity.kt   # paste invite, join, connect, status list
  app/src/main/generated/   # Kotlin bindings generated by uniffi-bindgen (not committed)
  app/src/main/jniLibs/     # libig_mobile.so per ABI (not committed)
  build-rust.sh
```

## Build

Requirements: Android Studio or the command line SDK, an NDK (r26 or newer), `cargo-ndk`,
the Rust Android targets, and a JDK between 17 and 23 (Gradle 8.10 does not run on newer
JDKs; set `JAVA_HOME` if your system Java is newer).

```sh
cargo install cargo-ndk
rustup target add aarch64-linux-android x86_64-linux-android
export ANDROID_NDK_HOME=~/Android/Sdk/ndk/<version>
android/build-rust.sh            # or: just android::core-build
cd android && ./gradlew assembleDebug   # or: just android::apk-build
```

`build-rust.sh` compiles `ig-mobile` for `arm64-v8a` and `x86_64` into `app/src/main/jniLibs`
and runs `uniffi-bindgen` to produce `dev.intergalactic.core` Kotlin bindings. Bindgen reads
its metadata from a host debug build of the same crate, because the stripped Android release
libraries carry none.

Verified: with NDK r27, cargo-ndk, Gradle 8.10.2 and JDK 21 the debug APK assembles, and
`lab/android/run.sh` runs it on an API 35 x86_64 emulator against a lighthouse and a Linux
node: VPN up, IPv4 and IPv6 traffic both ways, peer DNS inside the VPN.

## The tunnel switch

Off means off: the service pauses the engine, which closes every lighthouse session and
forgets its peers, and removes the VPN interface. Memberships stay. On resumes the engine,
which reconnects to every lighthouse and gets the peers back with the state pushes. The app
starts the engine paused when the tunnel was off, so an idle phone holds no sessions.

## Turning a network off on one device

Each network row has a switch. Off keeps the membership and the address (the lighthouse still
lists the device) but takes the network off this device: the VPN interface is rebuilt
without its address, route and DNS server, and the engine drops every packet for it in both
directions, so peers cannot reach the device there. The flag is stored with the membership
(`Membership.enabled`) and survives restarts. The desktop daemon honours the same flag (no
interface for a network that is off); the `ig` CLI has no command for it yet. After a network
is turned back on, peers that kept sending while it was off need up to about fifteen seconds
to re-handshake.

## Releases, signing and in-app updates

CI builds the APK on every release (`.github/workflows/ci.yml`, job `build-android`) and
attaches it as `intergalactic-<version>.apk`. The app checks the project's GitHub Releases
when it opens (at most every six hours, or from the menu) and offers any newer version in a
card; Install downloads the APK over the phone's normal connection and hands it to the
package installer. Pre-releases count as updates, because the app itself ships as
pre-releases for now. A local build is `0.0.0-dev`, so it always sees the newest release.

Android only installs an update that is signed with the same key as the installed app, so
every release is signed with one key that never enters the repository. It lives in four
repository secrets: `ANDROID_KEYSTORE_BASE64` (the PKCS12 keystore, base64), `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS` and, if it differs from the store password, `ANDROID_KEY_PASSWORD`. Keep a
backup of the keystore outside GitHub: a lost key means every phone must uninstall and
reinstall. To sign a local release build with the same key:

```sh
export IG_ANDROID_KEYSTORE=~/.config/intergalactic/android-release.jks
export IG_ANDROID_KEYSTORE_PASSWORD=... IG_ANDROID_KEY_ALIAS=intergalactic
IG_VERSION=0.0.0-dev gradle assembleRelease      # app/build/outputs/apk/release/app-release.apk
```

After an update, and after a reboot, `BootReceiver` brings the tunnel back when it was on
before (the VPN consent survives both). `IG_VERSION` sets `versionName`; `versionCode` is derived from it so a stable release
outranks its own pre-release. Debug builds use the debug key and cannot be updated in place
by a release: uninstall them first.

## Joining with a QR code

`ig-lighthouse invite create dev --qr` prints the invite as a QR code in the terminal, and
`ig invite show --qr <invite>` does the same for an existing invite (`--svg` writes an SVG for
a web page). In the app, Join network, then Scan QR code.

## Automation

The activity accepts an invite as an intent extra and can connect at once:

```sh
adb shell am start -n dev.intergalactic.app/.MainActivity --es invite "ig1:..." --ez connect true
```

The VPN consent dialog still appears the first time; `lab/android/run.sh` accepts it with
uiautomator.

The Gradle wrapper jar is not committed. Run `gradle wrapper` once, or open the project in
Android Studio, which generates it.

## How the app uses the engine

1. `EngineHolder.ensureStarted` creates `MobileEngine(stateJson, hostname, callbacks)`.
   The state JSON holds the private key and memberships; `generateState()` creates a new one.
2. `join(invite)` talks to the lighthouse and returns the network with the assigned address.
   The engine then fires `onNetworksChanged(networks, stateJson)`; the holder persists the JSON.
3. `IgVpnService` builds a `VpnService.Builder` with `addAddress` and `addRoute` for each
   network's IPv4 and IPv6 ranges, plus `addDnsServer` (the network's in-tunnel DNS responder)
   and `addSearchDomain`, calls `establish()` and passes the fd to `attachTun(fd)`. Only
   overlay CIDRs are routed into the VPN, so normal internet traffic is untouched. Peer names
   such as `laptop.dev.ig.internal` resolve on the phone while connected.
4. The engine calls `protectSocket(fd)` for its UDP and TCP sockets; the service answers with
   `VpnService.protect`.
5. On membership changes the service re-establishes the interface and attaches the new fd.

## DNS

Android has no split DNS: once a VPN adds DNS servers, every query from every app goes to
them. `addSearchDomain` only adds a suffix. So the in-engine responder must answer public
names too, not only `*.ig.internal`.

- The responder answers overlay names from its table. Unknown names under an overlay zone,
  and reverse lookups inside an overlay range, get NXDOMAIN locally.
- Every other name is forwarded. `IgVpnService` registers a `ConnectivityManager` callback
  for networks with `NET_CAPABILITY_INTERNET` and `NET_CAPABILITY_NOT_VPN`, reads their
  `LinkProperties.dnsServers` (Wi-Fi and Ethernet first, link-local addresses skipped) and
  calls `setUpstreamDns` on every change and after each `establish()`.
- The engine relays the raw query over a fresh UDP socket per query. It passes that socket
  to `protectSocket`, so `VpnService.protect` routes it over the underlying network and the
  query cannot loop back into the tunnel. Upstreams are tried in order with a 2 s timeout
  each; at most 64 forwards are in flight, more are dropped. The answer is written into the
  TUN with the responder address as source, exactly like a local answer.
- Desktop nodes pass an empty `upstream_dns` list and behave as before, because their OS
  resolver sends only overlay names to the responder.

Long-press a network in the list to leave it.
